# Универсальный художественный протокол: «Один кадр — один сюжетный момент» (v2)

**УТВЕРЖДЁННОЕ ПОСТОЯННОЕ ПРАВИЛО (с 14.11.2026):** генерация одной иллюстрации за один ход пользователя → визуальный REVIEW → подготовка и сохранение кандидата → мой ответ → ожидание следующего сообщения. Не генерировать 2 изображения в одном ответе даже ради исправления ошибки. См. [ART-ONE-IMAGE-CADENCE.md](ART-ONE-IMAGE-CADENCE.md). Это правило имеет приоритет над историческими упоминаниями генерации партиями по 4–6 кадров; пакетная **интеграция в игру** остаётся возможной после приёмки.

**Действует для всех дел «Бирмингем: Цена власти».** Это развитие первоначального протокола «один кадр — одна улика», **не второй параллельный процесс**. Историческая волна C01–C05 и уже установленные изображения сохраняются. При переходе в следующий чат открывать [ART-CONTINUATION.md](ART-CONTINUATION.md).

## Суть
Иллюстрация может передавать **атмосферу, разговор, действие, эмоциональное состояние, находку, переход или последствия**. В ней может не быть ни единой улики. Один кадр означает **один непрерывный момент/визуальный замысел**, а не одного персонажа и не один предмет. Несколько людей в живом диалоге или общий вид города — полноценные сцены.

Сначала сверить сценарий, персонажей и хронологию; затем классифицировать **функцию кадра**, а не просто ID. Доступны семь `sceneKind`:

| Тип | Назначение | Композиция |
|---|---|---|
| `environment` | Атмосфера города и локаций | Пространство, глубина, свет, настроение |
| `dialogue` | Разговоры, допросы, встречи | Жесты, лица утверждённых NPC, дистанция между участниками |
| `action` | Конфликты, бегство, передача предмета | Читаемое физическое действие, причинно-следственный момент |
| `emotion` | Страх, сомнение, утрата, предательство | Мимика/силуэт/жест, тихие детали |
| `evidence` | Осмотр следов, документов и предметов | Предмет в контексте, характерный признак |
| `transition` | Переезд, прибытие, смена места и времени | Событие и окружающая обстановка |
| `aftermath` | То, что осталось после происшествия | Пустота, следы, пространство, без выдумывания виновных |

## ДВА выхода из ОДНОЙ карточки (не два протокола)

1. **RENDER:** только положительные физические признаки — где происходит сцена, кто/что в ней, жест или событие, ракурс, 2–4 визуальных признака, фон и свет. Короткий текст **только о создаваемом изображении**. Никаких ссылок на соседние ID, статусы GitHub, QA, раскадровки, версии и запретные слова вроде названий ошибочных форматов.
2. **REVIEW:** отдельная карточка, которую **не отправляют** генератору: границы знания героя, неподтверждённые факты, запреты на спойлеры, проверка портретов, критерии отбора. Художественную приёмку делает ассистент, а не компьютерная проверка размеров.

Нельзя копировать объяснение о работе генератора в изображающий запрос. Прежняя ошибка: компилятор включал в одну строку `infographic`, `collage`, `approval` и сюжетные формулировки о доказательствах. Новая версия **никогда не включает `avoid` и `knowledgeBoundary` в RENDER**.

## Один компилятор для всех видов

```bash
# Визуальное задание ОДНОЙ сцены — текст можно использовать для отдельной генерации:
node docs/case002/art-wave-prompt-builder-v1.js --cards docs/case002/art-wave-17-shotcards-v1.json --id C07

# Совсем другой вывод: контрольная карточка, не для генератора:
node docs/case002/art-wave-prompt-builder-v1.js --cards docs/case002/art-wave-17-shotcards-v1.json --id C07 --review

# Пять РАЗНЫХ визуальных файлов. Никогда не объединять их в один запрос:
node docs/case002/art-wave-prompt-builder-v1.js --cards docs/case002/art-wave-17-shotcards-v1.json --all --out-dir /tmp/case002-shots
```

`schemaVersion:2` требует явный `sceneKind`. Для исторических карточек v1 оставлена совместимость; их нужно постепенно классифицировать, не меняя одобренную живопись.

## Правильная работа с генератором

- Перед **каждым** запуском использовать ровно один RENDER-промпт; не прикладывать общий план, прошлые коллажи, таблицу прогресса, отчёт об ошибке или все пять сцен.
- Нельзя ссылаться на сообщения/картинки с досками прогресса как на стилистические референсы: это приводит к повторному созданию плаката. Референс — только отдельная утверждённая **игровая сцена** или портрет нужного NPC.
- При двух последовательных возвратах плакатов/дубликатов — **остановиться** и изолировать контекст генерации (новая отдельная художественная постановка без производственных пояснений). Не пытаться подряд десятки раз и не коммитить заменитель.
- Компилятор *создаёт текст*, но **не управляет автоматически самим инструментом рисования**. Поэтому нельзя обещать, что одна только правка JS решит влияние контекста беседы на генератор. Финальный результат всегда оценивается визуально.
- Для персонажей: утверждённый портрет или безопасная композиция без неподтверждённого лица; не закреплять за кадром одного из пяти игровых героев без сценарного основания.
- Документальные цифры/время на изображении проверять отдельно: не объявлять правильной красивую картинку с неверными стрелками часов.

## Приёмка и выпуск

1. Художественная проверка против конкретной сцены, эмоции и пределов знания игрока.
2. Физическая подготовка WebP 720×900 (4:5), проверка RIFF, декодера, SHA-256, размера и сходства.
3. Готовые 4–6 кадров устанавливать одним атомарным коммитом `assets/case002/scenes/` + `src/case002/approved-art-v1.js`, после чего адресный art-CI и быстрый мобильный Chromium.
4. Стабильный `main`, Дело №001, граф и сохранения не менять. Нет новых механик.


## Практическая валидация и предел гарантии

Проверка на C09 дала предметный игровой кадр с самостоятельной композицией, но показала оставшийся грузовик и недостаточно ясное разделение трёх следов. Следующая попытка *редактирования этого кадра* в том же чате снова породила тематический инфографический плакат. Следовательно, автоматизация RENDER/REVIEW **работает как подготовка текста**, но текущий генератор всё ещё учитывает другую часть разговора; без отдельного явно изолированного художественного контекста не следует обещать заданный процент первых попаданий. Сохранять только визуально принятые кадры; повторную генерацию или правку запускать в отдельном чистом контексте, если инструмент позволяет. **Не создавать два разных протокола для улик и остальных сцен**.


## Отдельный источник истины для точных дат и цифр

Генеративный кадр не обязан содержать точное время, номера документов, подписи и математические данные. Если ошибка хотя бы одной цифры меняет канон, **выводить её штатным игровым HTML-текстом/диалогом**, где значение можно проверить детерминированно, а изображение оставить как физическую атмосферу момента. Не ретушировать и не использовать ошибочный текст, будто он верен. В данном этапе C06: `23:47` пишется сценарным текстом и не показывается на часах. Это **не меняет** сюжетный момент и не требует изменять движок/сохранения.


## Цикл обучения на ошибках (в производственном процессе)

После каждого отказа по изображению зафиксировать тип ошибки, коррекцию конкретного физического объекта/ракурса, критерий нового REVIEW и исход попытки в [art-generator-feedback-v1.json](art-generator-feedback-v1.json). Вызов `node tools/case002/art-feedback-v1.js --failure wrong_scene --same-context-attempts 2` сообщает о необходимости нового изолированного контекста. После двух промахов прекращать повтор в том же контексте. Это автоматизация *регламента работы*, не изменение весов модели рисования. Семантическую проверку доказательств, идентичности персонажей и спойлеров всегда выполняет художественный руководитель; WebP/SHA/dHash только дополняют её. Последний C09 получился на описании мокрой земли в крупном плане, двух колей и трёх самостоятельных цепочек следов слева, по центру и справа. Этот приём применяем к геометрически сложным уликам, а не ко всем художественным типам.


## Эксперимент: один игровой кадр за один художественный цикл (14 ноября 2026)

**По решению автора, начиная с D04 главы IV, временно меняется только размер партии: ОДНА сцена → ОДИН отдельный запрос RENDER → проверка результата по REVIEW → исправление / отказ / принятие → подготовка WebP и сохранение кандидата в feature-ветку → следующий эпизод в следующем цикле.** Не формировать заранее для генератора пять разных запросов одним пакетом и не запускать серию иллюстраций подряд в одной ответной итерации. Старый компилятор, карточки `sceneKind`, сценарий, актёрские референсы, история принятых иллюстраций и QA не меняются. Режим `--all` остаётся в компиляторе для обратной совместимости и тестов, но **не используется** при создании новых изображений этой главы.

Важные границы: техническая подготовка раскадровки целой главы возможна заранее, но генерация всегда по одной сцене; один кандидат ≠ установленное изображение; установка в игру остаётся отдельным управляемым действием после проверки и не должна ломать игровые статусы. Режим обратим: при худшем качестве / нестабильности вернуться к предыдущей процедуре художественных волн, сохранив уже проверенные файлы. Отмечать, какая попытка по счёту попала в сцену, но **не заявлять гарантированной точности на первом запросе** без подтверждающей статистики. После ошибок проверять фактически отправляемый запрос, а не только текст карточки.


## Уточнение автора: одна генерация, затем обязательный ответ (D05, 2026-11-14)

**Каждый ход работы = ровно одна новая иллюстрация для ровно одного сюжетного ID, затем художественный REVIEW, сохранение кандидата или отказ, короткий ответ автору и остановка генерации до следующего явного сообщения автора.** Даже если результат не подходит, **не запускать вторую генерацию в том же ответе**: пояснить, что не прошло REVIEW, зафиксировать ошибку, а новую попытку выполнить только в следующем пользовательском цикле. Не переходить к следующему ID до следующего сообщения автора. Это правило касается непосредственно вызовов image_gen; технические операции WebP, GitHub и CI после первой генерации допускаются в том же ходе. Причина эксперимента — замеченная автором возможная контекстная путаница при нескольких последовательных генерациях в одном ответе; гипотеза проверяется на реальных результатах и не выдаётся за доказанный механизм инструмента. RENDER/REVIEW и художественные критерии не меняются; при необходимости прежний режим восстанавливается отдельно.
