# ADR-0004 — телефон в приоритете, Telegram Mini App как следующий клиент

**Дата:** 2026-11-13  
**Статус:** accepted  
**Область:** игровая подача Дела №002, работа с телефоном и подготовка будущей Telegram Mini App.

## Контекст

Автор уточнил производственный приоритет: **в первую очередь реальные телефоны и будущий Telegram Mini App**. Полировка отдельного интерфейса ПК не является задачей данного этапа. Сценарный прототип №002 должен оставаться открываемым локально в Safari/Chromium без внешней сети и Telegram SDK. Живую интеграцию Mini App нельзя называть готовой.

## Решение

1. **Основная цель UX:** вертикальный телефон: 360, 390 и 430 CSS px, касания от 44 CSS px, доступные реплики, выборы, улики и уведомления. Дополнительно проверяется узкий экран 320 px. ПК обязан оставаться функциональным, но отдельные широкоформатные художественные панели, анимации и сложная адаптация не в приоритете.
2. Никакие изображения не должны перекрывать реплики, кнопки или оперативную панель дела. Для каждой принятой сюжетной сцены при возможности готовится отдельный вертикальный WebP с безопасной композицией, зарегистрированный только при наличии файла. Если вертикальный файл отсутствует, сохраняется горизонтальный master; если он испорчен или не загрузился, экран остаётся управляемым.
3. При наличии Telegram WebApp bridge подключается локальный [адаптер безопасных областей](../../src/case002/telegram-safe-area-v1.js): суммирует аппаратные `safeAreaInset` и элементы Telegram `contentSafeAreaInset` для каждой стороны, обновляет CSS-значения по `safeAreaChanged`, `contentSafeAreaChanged`, `viewportChanged`. Значения ограничиваются разумным числовым диапазоном, не влияют на сюжет и сохранение.
4. Для обычного браузера без Telegram WebApp применяется нулевая переменная адаптера и стандартное `env(safe-area-inset-*)`. В CSS используется `max` с системным `env`, чтобы не применять один аппаратный отступ дважды.
5. Никаких сетевых SDK, Telegram-авторизации или серверного аккаунта на этом этапе. Не менять `localStorage` №001 или сюжетные переходы №002.
6. Проверки: быстрый мобильный Chromium после верстки и арт-изменений, отдельный WebKit/Chromium при больших изменениях, полный набор 400 сценариев — только при изменениях графа, контракта, движка, сохранений или релизной приёмке.
7. При любой серьёзной несовместимости WebKit/Telegram UX исправлять сначала мобильное поведение; улучшение ПК не может быть причиной регрессии на телефоне.

## Альтернативы

- Полировать параллельно уникальную desktop-версию — отвергнуто до завершения мобильной сюжетной кампании.
- Загружать SDK через CDN в обязательном порядке — отвергнуто для локального HTML-прототипа: он должен открываться без сети.
- Учитывать только iPhone notch, игнорируя Telegram controls — отвергнуто: в Telegram существуют две самостоятельные зоны.
- Показывать пустой экран, если портретный WebP повреждён, — отвергнуто: разрешён безопасный fallback на уже проверенный landscape.

## Последствия

- UI делается ради игрока на телефоне. Подключение Telegram SDK позже потребует отдельного этапа, интеграционных проверок и согласования публикации.
- `main` и существующее Дело №001 остаются стабильными.
- Изменены только модули представления, документация и выборочный QA.
